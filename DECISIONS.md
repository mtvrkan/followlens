# DECISIONS.md — professional defaults chosen during the rebuild

Ambiguous calls resolved without blocking, per the working rules. Each entry: what was decided, and why.

1. **Upgrade in place, not a ground-up rewrite.** The audit that opened the rebuild found the codebase already on the target architecture (MV3, Vite + CRXJS, strict TS, adapter pattern, 85 passing tests). A rewrite would have discarded live-verified platform heuristics (Instagram dialog detection, X GraphQL tree-scan) for zero architectural gain. Everything else in the plan was applied as targeted changes.

2. **Hybrid i18n: `chrome.i18n` for the manifest, i18next for the UI.** `chrome.i18n` cannot switch language at runtime (it is pinned to the browser UI language), and the in-app language switcher is an existing feature worth keeping. So the store-visible strings (name, description, on-page indicator) live in `_locales/`, while all UI strings stay in i18next catalogs. Internal codes are bare (`pt` carries pt-BR content, `zh` carries zh-CN) so i18next's `languageOnly` normalization maps regional variants onto them; `_locales` uses Chrome's `pt_BR`/`zh_CN` naming.

3. **Static host permissions instead of `optional_host_permissions`.** Runtime-granted hosts would require replacing manifest-declared content scripts with `chrome.scripting.registerContentScripts` (plus the `scripting` permission) and re-registering on every startup, including a MAIN-world script. That trades a simple, reviewable 4-host manifest for meaningful complexity and new failure modes. The four hosts are individually justified in STORE-LISTING.md instead.

4. **Custom ~70-line toast instead of a Radix Toast dependency.** Needs are: two tones, auto-dismiss, `aria-live`. A dependency (swipe gestures, viewport hotkeys) is not warranted at this size.

5. **Auto-collection kept, but strictly gesture-gated.** Auto-scroll (and GitHub's auto-pagination) never starts on its own: the popup's "Start Auto-Collect" button switches it on per tab, an on-page shadow-DOM pill shows live progress with a Stop button, and a successful save switches it back off. Passive collection (data the user loads by scrolling themselves) still works with collection off. The per-tab flag persists in `sessionStorage` only so GitHub's full-page pagination can resume — it dies with the tab.

6. **Avatar durability caps: 64 KB per image, 2 000 conversions per page session.** Data-URL conversion defeats CDN hotlink protection/URL expiry but multiplies storage; past the caps the original URL is kept and the Avatar component degrades to initials if it later expires.

7. **Scan buffer in IndexedDB (Dexie v2), not `chrome.storage.session`.** Session storage's 10 MB quota is exceeded by a few thousand data-URL avatars, failing large scans wholesale. The `bufferUsers` table's compound primary key also dedupes re-reported users for free. Snapshot save/clear stays serialized behind the background message queue.

8. **Message envelope is `Result<T>` everywhere.** Responses are JSON-serialized, so handlers must resolve to `null` rather than `undefined` (a stripped `value: undefined` would read as malformed). `sendRuntimeMessage`/`sendTabMessage` never throw; every caller branches on `ok`.

9. **`use_dynamic_url` left as CRXJS emits it.** CRXJS 2.x manages the `web_accessible_resources` entries it generates for its loaders; overriding them by hand risks breaking script loading and the entries expose no user data. Revisit if CRXJS adds first-class support.

10. **Icons kept as placeholders.** Proper branded icons (16/48/128 + store tile) were a design asset outside this rebuild's scope; the store checklist in STORE-LISTING.md flagged them as the one remaining pre-submission asset. *No longer current:* the mark is drawn — a lens with two accounts inside it — and 16/48/128, both store tiles, the favicon, the social card and the in-app header all render that one drawing.

11. **Active list paging (`selfFetch`) kept, but disclosed and user-switchable.** This is the one place the extension requests something the user's own browsing wouldn't have: Instagram's own list endpoint (asked from that page, with the session already signed in) and GitHub's public REST API. It exists because scroll-only reading was measured live to miss real followers, and a missing follower surfaces downstream as a *wrong* "doesn't follow back" entry — the product's core claim. Kept on by default because turning it off measurably degrades scan completeness, but: exposed as a Settings switch ("Faster, more complete scans"), spelled out in PRIVACY.md and in the store-review notes, capped (Instagram: page size 12, ≤2 000 enumerable accounts, wide random pacing, 3-hour per-platform cooldown after any rejection), and never touching an account other than the one whose list the user asked to scan. The earlier docs claimed the only network activity was avatar re-fetching, which was simply untrue once `selfFetch` existed; that has been corrected rather than left as a favourable inaccuracy.

12. **The MAIN-world script is registered for `matchRequest` *or* `selfFetch` adapters.** It was `matchRequest` only, which silently excluded GitHub — so `START_SELF_FETCH` was posted into a world where nothing was listening, every GitHub scan burned its 5-second watchdog before falling back, and the adapter's whole self-fetch path was unreachable code. Registering on either capability is what makes the manifest match the code's actual requirements. Two CORS constraints came with it, both encoded in the capability rather than hardcoded: `credentials: 'omit'` for a wildcard-CORS public API (a credentialed request against `Access-Control-Allow-Origin: *` fails outright), and only CORS-safelisted request headers, which cost GitHub's documented `X-GitHub-Api-Version` pin — a preflight GitHub does not allow from a page origin would have failed the request rather than just dropping the header.

13. **Diff identity is username-first, `id` second.** `id` looked like the more stable key (it survives a handle rename) but is not comparable across sources: one scan mixes Instagram's DOM scrape (`id` = username) with its API path (`id` = numeric pk), and GitHub's scrape with its API the same way. Keying on `id` first therefore reported the same person as a different one whenever two scans — or the two directions of one scan — were collected via different paths, producing mass false "unfollowed you" and false "not following back" results. Username matches across every source and is already the buffer's dedup key; `id` remains as the secondary match, so rename detection is kept.

14. **Diagnostic logging off by default, with a Settings switch.** The `[FollowLens]` logs are how every platform heuristic was derived and remain the only way to diagnose "collected nothing" in a user's own browser — but unconditional logging meant every install printed to the console on every visit to a supported site, whether or not a scan was running. The flag lives in `chrome.storage.local`; because the MAIN-world script has no `chrome` API at all, the content script mirrors the flag onto `<html>` as a data attribute, which is the one channel both worlds share. Genuine errors are not routed through the switch.

15. **No bundled webfont.** `body` asked for `'Inter'` first with no `@font-face` and no font in the package — so it applied only for users who happened to have Inter installed locally, meaning the same UI rendered with different metrics for different people. A strict CSP rules out fetching it remotely and bundling it costs ~100 KB for a difference the design was never tuned against, so the platform UI stack is now the explicit choice.

16. **The badge is restored on service-worker start.** Badge text is per-browser-session UI state that Chrome never replays, so the stored per-account unfollow counts have to be pushed back on startup; otherwise the number silently vanished after every browser restart and only returned after the next save.


17. **TikTok and X removed outright, rather than left registered-but-disabled.** X was already disabled: it pads short follower/following lists with algorithmic "who to follow" suggestions that live testing found indistinguishable from real entries in the response, producing large over-counts (and, when a naive filter was tried, under-counts just as bad). TikTok's only workable collection path was intercepting its own list responses — its API signs every request with `X-Bogus`/`X-Gnarly`, computed by an obfuscated in-page VM over the full URL, so the extension can neither construct a request of its own nor reuse an observed signature (the cursor it would have to change is what the signature covers), and the signer is no longer reachable as a stable page function. Both platforms could therefore produce follower data that was wrong rather than merely incomplete, and a wrong "doesn't follow back" answer is worse than no answer. Keeping them registered-but-disabled had been the pattern (so old scans still rendered), but it kept dead adapters, their host permissions in the manifest, and their branches through shared code alive for platforms with no path back. Removing them drops `tiktok.com`, `x.com` and `twitter.com` from the requested host permissions entirely. Consequence accepted: snapshots already saved for those platforms stay in IndexedDB but are no longer listed anywhere, and are not deleted — that is the user's call, not an upgrade's. Backups containing them import their remaining platforms instead of being refused (see `RETIRED_PLATFORMS` in `lib/backup.ts`).

18. **The toolbar badge was removed** (superseding decision 16, which describes how it used to be restored). The red count on the extension icon showed the lost-follower total from the last *saved* scan, summed across accounts. Saving is a manual action here — nothing collects in the background — so the number was never a notification of anything new; it was however stale the last save happened to be, it could not clear itself, and it routinely disagreed with what the dashboard showed. Removing it also drops the `badgeCounts` storage key, the per-account bookkeeping in account deletion, and the start-up restore that existed only because badge text is per-session browser state Chrome never replays. Earlier versions' leftovers are cleared once on worker start-up (`clearLegacyBadge`), on start-up rather than on install because an install event never fires for a user who only gets the update.
